# Repo Audit — August 2026

A deep-dive of what the repo promised vs. what it actually did, plus a code
quality review. Items marked ✅ were fixed in the same change that added this
document; items marked ⚠️ are known issues left for follow-up.

## Promises vs. reality (before this change)

| Promise | Reality |
|---|---|
| README: "100% legal, no LinkedIn automation" | A full Playwright automation package existed (`src/linkedin/automation/`) with login, connect, message, search, scrape actions. ✅ README now describes the automation honestly, with a ToS warning. |
| README documented `automate search / import-search / profile` | **No `automate` command group existed at all.** The actions were library code wired to nothing; the only similarly-named group (`automation`) manages cron scheduling. ✅ Implemented the full `automate` group. |
| "Daily safety limits (20 connections, 25 messages)" | Limits were in-memory only — every new CLI process reset them to zero, so the caps never actually held across runs. ✅ Counters now persist per-day in `~/.linkedin-cli/automation_usage.json`. |
| Session persistence via cookies | `browser.py` only *loaded* saved state when `user_data_dir` was set, but *saved* it under `cookies_path` — with the CLI defaults the saved session was never restored. ✅ Fixed. |
| Posting, liking, profile editing, job applying | Did not exist in any form. ✅ Added: `automate post/engage/sync-profile/easy-apply` + page-object methods + actions with limits and dry-run. |
| `data backup` "backup of all data" | Backups silently omitted `applications.json`, `conversations.json`, `content_calendar.json`, `interview_prep.json` — restore lost all of them. ✅ Fixed. |
| Resume/job-application linkage | None. Applications tracked text only. ✅ Added the resume-repo bridge (`LINKEDIN_RESUME_REPO`, variant matching, autoapply import). |

Undocumented-but-existing commands (now in README): `analytics` group,
`optimize` group. Still undocumented: `templates list`, `applications delete`,
`automation env set-anthropic-key`.

## Bugs found and fixed ✅

- `LinkedInPage.get_search_results()` returned the profile link under key
  `"url"` while `import_search_results()` read `"linkedin_url"` — live search
  imports silently dropped every profile URL (tests passed because they
  hand-crafted dicts). Canonical key is now `linkedin_url`.
- `data export all -o contacts.csv` produced `companies_companies.csv` for the
  companies file (double string-replace).
- CSV import of contacts/companies **without an `id` column** wrote records
  with no `id` key, after which every `get/update/delete` raised `KeyError`
  and the CRM was unusable. Ids are now always assigned.
- `analytics summary`/`velocity` crashed (`ValueError`/`TypeError`) on any
  contact whose `created_at` carried a `Z` suffix or timezone offset (e.g.
  imported data). Dates are now parsed defensively.
- CLAUDE.md documented the wrong env var name for the draft fallback
  (`LINKEDIN_DRAFT_FALLBACK` → actual: `LINKEDIN_AI_FALLBACK_ENABLED`).

## Known issues (not fixed here) ⚠️

- **DB backend data loss**: with `LINKEDIN_BACKEND=db`, `resume_text` is
  dropped from profiles (no column), contact `referral_contact_id` is not
  written on update, and campaign/template-usage state has no columns at all —
  those features are silent no-ops on the db backend. Needs a model +
  migration change.
- **Run-lock races**: stale-lock clearing in `run-daily` is check-then-unlink
  (not atomic), and `--watch` mode holds one lock for days without refreshing
  it while the cron TTL is 180 min — a scheduled run will eventually declare
  the watcher stale and run concurrently.
- **`contacts merge --prefer duplicate`** swaps record identities, so the
  *primary* id is what gets deleted — contradicting the CLI help. Merge also
  leaves applications/conversations/drafts pointing at the deleted duplicate id.
- **No atomic JSON writes**: `save_json` writes in place; a crash mid-write can
  corrupt a store file. A tmp-file + `os.replace` pattern would fix it.
- Analytics conversion funnel counts `rejected` contacts as still "in funnel"
  at every stage; calendar dates are compared as raw strings with no format
  validation at `calendar add`.
- Easy Apply and the profile-edit selectors are best-effort against LinkedIn's
  current DOM; LinkedIn changes markup frequently, so expect selector
  maintenance (same caveat the resume repo's autoapply README makes).

## Architecture decision: two repos, bridged

The resume repo already contains a complete apply loop (sources → match →
build PDFs → fill → submit) for Greenhouse/Lever/Ashby plus aggregator
scraping, with its own profile.yml and SQLite state. Consolidating it into
this repo was considered and rejected: the LaTeX build, ATS appliers, and
game/dashboard are self-contained and healthy there. Instead this repo reads
the checkout directly (stdlib only — variant dirs, `skills.tex`, `output/`
PDFs, `state.db`) so:

- LinkedIn Easy Apply here uses the same variant PDFs autoapply builds.
- `applications import-autoapply` gives one unified application tracker here.
- Nothing in either repo imports the other's code.
